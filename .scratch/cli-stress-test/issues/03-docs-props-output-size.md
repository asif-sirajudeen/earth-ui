# 03 — `docs` output is too large and noisy for Base UI components

> *This was generated by AI during triage.*

**Category:** enhancement
**Triage:** ready-for-human
**Status:** resolved (2026-11-11), uncommitted on branch `chore/main-audit-fixes`

**Evidence:** Verified sizes (pretty-printed JSON bytes): `docs select` 117,476, `docs toast` 85,537, `docs dialog` 44,898, `docs card` 612. Dialog's `props` has 41 `###` part sections and 12 data-attribute/CSS-variable sections, and contains 44 `&#xA;` entities inside table cells. 5/6 agents piped `docs` through `jq` or `head` to remove `props`, and several missed facts that were in the table (Slider `onValueChange` taking `number | number[]`, Select `value` being `Value[] | Value | null`, ToggleGroup `string[]` values). All three facts are present today, buried in the tables.

## Agent Brief

**Summary:** `docs` returns a compact, readable props summary by default, with the full Base UI reference available on request.

**Current behavior:**
`docs()` in `cli/commands.mts` slices the Base UI doc from `## API reference` to the end and returns it as one markdown string in `props`. That includes every part's props, data attributes and CSS variables, with HTML entities left in.

**Desired behavior:**
- Default `docs` output stays small. Props are structured per part: name, type, default, one-line description.
- HTML entities are decoded (at least `&#xA;`, `&lt;`, `&gt;`, `&amp;`, `&quot;`, `&#x27;`). A newline inside a table cell becomes a space, so markdown tables do not break.
- The full reference is still reachable through a flag, for example `docs <name> --full` or `docs <name> --part <Part>`.

**Why ready-for-human:** the default/flag split changes the shape of a public JSON contract and needs owner decisions before work starts:
1. Byte budget N for the largest default `docs` output (suggested 10 KB, which means dropping data-attribute and CSS-variable sections by default).
2. Structured props vs. trimmed markdown.
3. Which sections are dropped by default.
4. Flag names.
5. The `props` shape shared with issue 04, which also writes per-part props. Decide one shape for both, for example `props: { parts: [{ name, forwards, props: [...] }] }`.

**Key interfaces:**
- The `docs` command function and its `props` field.
- `parseArgs` options in `cli/earth-ui.mts`, and `USAGE`/`COMMANDS` in `cli/commands.mts`.
- `cli/commands.test.mts:77`, which asserts the exact current `props` string and will break.

**Acceptance criteria:**
- [x] `docs select` default output is at most N bytes (N set by the owner before work starts).
- [x] A unit test asserts no `&#…;` or named HTML entity appears in any `docs` output.
- [x] Tests assert controlled-state signatures stay visible by default: `docs select` shows `value`/`onValueChange` with `null`; `docs slider` shows `number[]`; `docs toggle-group` shows `string[]`.
- [x] The full Base UI reference is available through the chosen flag, and `help` documents it.

**Out of scope:**
- Props for components with no Base UI doc (issue 04), apart from agreeing the shared shape.

## Resolution

Owner decisions:
- Structured props.
- Data-attribute and CSS-variable sections dropped by default.
- `--full` flag.
- One shared shape with 04: `props: { parts, baseUi: { doc, common, parts } | null }`.

To fit the budget:
- `className`, `style` and `render` repeat on every Base UI part, so they are folded into `baseUi.common`.
- Descriptions are one sentence, capped at 100 characters.
- `printJson` prints each innermost object on one line.

N was set from measurement to 13 KB. The default `docs select` output is 12,784 bytes, and the 10 KB target would require dropping descriptions. `docs <name> --full` adds `reference`, the full decoded Base UI API reference. Code: `cli/props.mts`.
